## 먼저 수정할 문제

### 1. P1 — 자산 이름이 HTML과 스크립트로 실행된다

- 위치: `src/main/resources/static/js/app.js:604–609`, `:552–558`, `:1462` 등.
- 자산 이름은 API에서 저장할 수 있는 사용자 입력인데, 본문과 `data-asset-name` 속성에 escaping 없이 삽입된다.
- 임시 계정의 BANK 이름에 `<img src=x onerror="document.title='Folio XSS reproduced'">`를 저장한 뒤
  대시보드에 로그인하자 브라우저 제목이 실제로 `Folio XSS reproduced`로 바뀌었다.
- 영향: 해당 값을 표시하는 사용자 브라우저에서 스크립트 실행. 현재 자산은 사용자별로 격리되어 있으므로
  타인에게 해당 값을 심는 경로나 계정 간 공격까지 확인한 것은 아니다.
  다만 같은 origin의 localStorage에 Access/Refresh Token을 저장하므로 스크립트 실행 시 토큰 접근도 가능한 구조다.
- 수정: 사용자 문자열을 출력하는 모든 HTML 본문·속성 경로를 확인하고 `textContent` 또는 적절한 escaping을 적용한다.
  이름 외 메모·오류 메시지·폼 value도 함께 확인한다. CSP는 추가 방어로 검토한다.
- 완료 기준: 저장 → 조회 → 목록·상세·수정·거래 폼을 반복해도 문자열로만 표시되고 스크립트가 실행되지 않는다.

### 2. P1 — HTTP 배포 가이드와 거래 화면의 브라우저 요구사항이 맞지 않는다

- 위치: `docs/AWS_DEPLOYMENT.md:49`, `deploy/aws/docker-compose.yml:48–49`,
  `src/main/resources/static/js/app.js:2138`, `:2855`, `:2932`.
- 가이드는 외부 `http://EC2_PUBLIC_IP:8080` 접속을 안내하지만 거래 폼은 `crypto.randomUUID()`를 직접 호출한다.
  이 API는 secure context가 필요하다. 일반적인 외부 HTTP origin에서는 사용할 수 없어 이벤트 등록 전에 폼 초기화가 실패할 수 있다.
- 로컬 루프백 접속과 API 스크립트 성공은 이 문제를 검증하지 못한다. 이번에는 실제 EC2 브라우저에서 재현하지 않았으며,
  코드와 [브라우저 API 문서](https://developer.mozilla.org/en-US/docs/Web/API/Crypto/randomUUID)에 근거한 판단이다.
- 수정: 실제 사용할 도메인의 HTTPS 진입점을 구성하고 앱 8080 직접 공개를 제한한다.
  프록시 도입 시 `AuthRateLimitFilter`의 IP 판별도 신뢰할 프록시에 한정해 구성한다.
- 완료 기준: 외부 기기에서 HTTPS로 가입·로그인·매수·매도·입금·출금이 모두 동작한다.

### 3. P1 — MySQL 자동 재시작 설정이 없다

- 위치: `deploy/aws/docker-compose.yml:2–20`. 앱에는 `restart: unless-stopped`가 있지만 MySQL에는 없다.
- Docker 기본 restart policy는 `no`이므로 DB 종료나 호스트 재시작 뒤 DB가 자동 복구되지 않을 수 있다.
  `depends_on`은 이 누락을 보완하는 재시작 정책이 아니다.
  [Docker 공식 문서](https://docs.docker.com/engine/containers/start-containers-automatically/)
- 수정: DB 재시작 정책과 호스트 Docker 자동 시작을 설정한다. Compose 로그 용량 제한도 함께 정한다.
- 완료 기준: 격리 환경에서 DB 비정상 종료 및 호스트 재시작 후 health와 기존 계정·자산이 복구된다.
  볼륨을 삭제하는 방식으로 검사하지 않는다.

### 4. P1, AI 활성화 전 — 일일 예산이 엄격한 호출 상한은 아니다

- 위치: `evidence/agent/LlmUsageBudgetService.java:27–57`,
  `FinancialEvidenceAgentService.java:142–165`, `news/NewsSummaryWorker.java:40–43`.
  모두 `src/main/java/com/assetdashboard/` 아래다.
- 현재 흐름은 사용량 조회 → 외부 호출 → 성공 반환 후 카운터 증가다.
  예를 들어 200회 중 199회를 썼을 때 여러 요청이 함께 검사하면 모두 통과할 수 있다.
  한 인스턴스에서도 사용자 요청과 뉴스 Worker가 겹칠 수 있다.
- 외부 처리가 이뤄졌지만 응답 파싱·형식 검증·응답 수신에 실패하면 성공 후 기록 경로까지 도달하지 못한다.
  이 경우 호출 카운터에서 빠질 수 있으며, 사용자가 다시 시도하면 실제 호출량과 차이가 커질 수 있다.
- 수정: 외부 전송 전에 원자적으로 호출 예산을 예약한다. 실패·사용량 미확인·정상 응답을 구분해 기록하고,
  토큰은 사후 집계 기준인지 사전 예약 상한인지 명확히 한다. 비멱등 외부 POST 재시도 금지는 유지한다.
- 완료 기준: 한도 직전의 동시 요청, 응답 유실, 형식 오류를 mock으로 재현해 예약량·실제 호출 수를 검사한다.
- 초기 배포에서 AI를 비활성으로 유지하면 이 항목을 AI 공개 시점으로 분리할 수 있다.
  현재 AWS Compose에는 AI 활성화·키·예산 환경변수 전달도 없어 별도 연결이 필요하다.

### 5. P2 — 일반 사용자에게 운영 지표가 노출된다

- 위치: `src/main/java/com/assetdashboard/global/config/SecurityConfig.java:86–87`,
  `src/main/resources/application.yml`의 management 노출 설정.
- 인증 여부만 확인하므로 새로 가입한 일반 계정도 JVM·HTTP·DB 풀 등의 운영 지표를 조회할 수 있다.
  임시 일반 계정으로 `/actuator/metrics` 200 응답을 확인했다.
- 수정: 운영 지표를 내부 접근 또는 운영자 권한으로 제한한다. 일반 계정과 운영자 접근을 나누어 검증한다.

### 6. 운영 필수 — 서버 밖 자동 백업과 복구 확인이 필요하다

- 위치: `deploy/aws/backup.sh:18`, `deploy/aws/verify-backup.sh`, `docs/AWS_DEPLOYMENT.md`.
- 저장소에는 수동 백업·임시 DB 복구 검증 도구가 있지만, 기본 저장 위치는 같은 호스트의 `backups` 폴더다.
  서버 저장장치를 잃으면 원본과 백업을 함께 잃을 수 있다. 서버 외부 자동 보관·예약 실행·실패 알림 설정은
  저장소에서 확인되지 않았으며 실제 AWS 설정은 미확인이다.
- 완료 기준: 예약 백업 성공 → 서버 외부 사본 확인 → 해당 사본으로 격리 DB 복구 → 데이터 비교까지 확인한다.

## 후속 확인 항목

- 여러 브라우저 탭에서 토큰 만료가 겹치면 현재의 탭 내부 Promise만으로는 갱신을 조정할 수 없다.
  같은 Refresh Token의 재사용 판정으로 정상 사용자 세션이 폐기되는지 두 탭에서 재현하고 조정한다.
- 공개 가입을 받을 경우 이메일 소유 확인·비밀번호 분실 복구·문의 경로를 결정한다.
- 실제 사용할 주식·코인·환율 데이터의 조회 성공과 오류 표시를 서버에서 확인한다.
- UI 자동 검증이 CI에 없어 현재 230개 Java 테스트만으로 브라우저 보안을 보장하지 못한다.
- 기존 운영 체크리스트의 '구현 완료'와 새 배포 환경에서의 '운영 검증 완료'를 구분한다.

## 권장 진행 순서와 배포 완료 기준

1. 화면의 사용자 문자열 출력 문제를 고치고 브라우저 회귀 검증을 추가한다.
2. MySQL 재시작, 운영 지표 접근, 로그 용량 제한, HTTPS 및 프록시 IP 구성을 정리한다.
3. 운영과 같은 MySQL에서 V1~V13 마이그레이션과 스키마 검증을 실행한다.
   빈 DB뿐 아니라 기존 배포 버전의 백업 사본을 새 버전으로 올리는 경로도 검사한다.
4. 서버 외부 백업·격리 복구와 이전 앱 버전으로 되돌리는 절차를 검증한다.
   스키마가 바뀌었다면 이전 앱 이미지 실행만으로 롤백이 된다고 가정하지 않는다.
5. 외부 HTTPS 주소에서 두 테스트 계정으로 소유권, 거래 중복 방지, 금융 계산, 세션 갱신,
   데이터 유지, 외부 시세 장애와 정상 복귀를 검증한다. PC와 모바일의 주요 폼도 확인한다.
6. 소수 사용자 베타를 시작하고 장애·백업 실패를 알 수 있는 상태를 만든다.
   AI는 호출 예산 수정·mock 검증과 운영 설정을 마친 뒤 별도로 활성화한다.

초기 목표는 현재 구조를 유지한 단일 인스턴스 베타다. 다중 인스턴스, Redis, Kubernetes,
멀티 Tool 확장은 이번 수정의 선행 조건으로 삼지 않는다.
