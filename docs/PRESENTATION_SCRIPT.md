# Folio 발표 대본과 개념 학습 노트

> 대상: 현직 팀장·개발자에게 개인 프로젝트를 설명하고 설계 피드백을 받는 자리
> 권장 시간: 발표 8~10분 + 데모 4~5분 + 질의응답
> 목표: 기능의 개수보다 **문제를 정의하고, 틀린 숫자를 막고, 선택의 근거를 설명할 수 있음**을 보여준다.

---

## 0. 발표 전에 기억할 한 문장

> Folio는 여러 자산을 예쁘게 모아놓은 화면이 아니라, 수동 입력과 외부 데이터의 불확실성 속에서도 **현재 가치·원가·손익의 의미가 섞이지 않게 설계한 개인 자산 대시보드**입니다.

발표 중 길을 잃으면 이 문장으로 돌아온다.

---

## 1. 10분 발표 대본

아래 인용문은 그대로 말해도 되는 문장이고, `화면` 표시는 발표자가 할 동작이다.

### 1-1. 시작 — 40초

> 안녕하세요. 제가 만든 프로젝트는 Folio라는 개인 자산 대시보드입니다.
> 은행 잔액은 은행 앱에 있고, 해외주식은 증권 앱에 있고, 암호화폐는 거래소에 있다 보니 전체 자산을 이해하려면 여러 앱을 돌아다녀야 했습니다.
> 그래서 현금·은행·국내외 주식·암호화폐를 직접 기록하고, 최신 시세와 환율을 결합해 원화 기준으로 한눈에 보는 MVP를 만들었습니다.

> 다만 주문 실행이나 MyData 연동까지 넓히지는 않았습니다. 이번 프로젝트에서는 범위를 수동 입력형 Portfolio로 제한하고, 숫자의 정합성과 사용자가 실수했을 때의 복구 경험에 집중했습니다.

핵심 메시지: “크게 만든 서비스”가 아니라 “작게 정의하고 깊게 고민한 서비스”다.

### 1-2. 문제 정의와 범위 — 50초

> 처음에는 자산을 등록하고 평가금액을 합치면 끝이라고 생각했습니다. 그런데 실제로 입력해 보니 어려운 부분은 화면이 아니라 숫자의 의미였습니다.
> 예를 들어 미국주식을 과거 1,520원 환율에 샀는데 현재 환율로 원가까지 다시 계산하면 과거 취득원가가 바뀝니다. 또 USDT 자산을 팔았는데 원화 현금이 늘어나는 것도 실제 자금 흐름과 다릅니다.
> 그래서 이 프로젝트의 핵심 질문을 세 가지로 좁혔습니다. 현재 가치와 과거 원가를 어떻게 분리할 것인가, 매매와 현금 이동을 어떻게 함께 기록할 것인가, 외부 시세를 모를 때 어떤 숫자를 보여줄 것인가입니다.

### 1-3. 제품 시연 — 2분

`화면: 로그인 후 Dashboard`

> 첫 화면은 기록 화면이 아니라 조회 화면입니다. 사용자는 들어오자마자 총 투자자산, 오늘 손익, 보유 Position, 통화별 투자 대기자금과 현재 환율을 볼 수 있습니다.

`화면: 총자산 옆 눈 아이콘 클릭`

> 금액을 다른 사람 앞에서 확인할 때를 위해 개인정보 금액을 한 번에 가릴 수 있게 했습니다. 이것은 보안 기능이라기보다 어깨너머 노출을 줄이는 UX입니다.

`화면: 오늘 손익 클릭 → Asset Analysis`

> 오늘 손익은 단순 텍스트가 아니라 분석 화면으로 연결됩니다. 09시를 하루 기준으로 Snapshot을 만들고, 입금과 출금은 손익에서 빼서 실제 시장 변동에 가까운 Daily PnL을 보여줍니다.

`화면: Folio 로고 클릭 → Dashboard 복귀, BTC 또는 ZEC 행 클릭`

> 자산을 누르면 현재 수량, 원통화 평균 매수가, 원화 손익과 거래 이력을 확인할 수 있습니다. 매수·매도는 같은 통화의 투자 대기자금과 함께 움직입니다. 예를 들어 USDT 기준 자산을 팔면 원화가 아니라 USDT 대기자금이 증가하고, 전체 총액에서만 현재 USDT/KRW 환율로 환산합니다.

`화면: 보유 수량 정정 버튼을 가리킴`

> 최초 수량을 14.7이 아니라 15.7로 잘못 입력한 경우 1개를 가짜 매도하지 않습니다. 가짜 매도는 실현손익을 만들기 때문입니다. opening position을 정정하고 기존 거래를 다시 계산하는 별도 흐름을 뒀습니다.

`화면: + → 자산 등록 → 주식 → SK 검색`

> 국내주식은 사용자가 Yahoo 형식인 000660.KS를 외우지 않아도 됩니다. KRX 상장 목록을 로컬에서 검색해 SK하이닉스를 선택하면 사용자 심볼과 외부 조회용 심볼을 분리해 처리합니다.

### 1-4. 도메인 설계 — 1분 20초

> 도메인의 중심은 Asset입니다. Asset을 Aggregate Root로 두고 수량, 평단가, 실현손익은 Asset의 도메인 메서드에서만 바뀌게 했습니다. TransactionService는 어떤 순서로 조회하고 저장할지를 조율하지만 계산식 자체를 소유하지 않습니다.

> Transaction은 Asset에 종속된 사건 기록입니다. 다만 거래가 계속 늘어나는 컬렉션을 Asset 조회 때마다 전부 가져오지 않기 위해 별도 Repository로 저장했습니다. 대신 거래를 보기 전에 부모 Asset의 소유권을 반드시 확인합니다.

> 최초 보유 수량은 과거 매수 Transaction으로 위장하지 않고 opening position으로 분리했습니다. 사용자는 이 서비스를 쓰기 전부터 자산을 갖고 있을 수 있기 때문입니다. 매수 이력이 없는데 가짜 매수를 만들면 거래 내역의 의미가 거짓이 됩니다.

### 1-5. 다중 통화와 환율 계약 — 1분 30초

> 외화 자산은 현재 가치와 취득 원가에 서로 다른 환율이 필요합니다. 현재 평가금액은 수량 곱하기 현재가 곱하기 현재 환율입니다. 반면 원화 평균 매입단가는 각 매수 시점의 가격과 환율로 확정하고 나중에 바꾸지 않습니다.

> 여기서 실제 버그를 하나 겪었습니다. 과거 거래에 환율을 생략하면 오늘 환율이 원가에 들어갔습니다. 처음에는 백엔드에서 과거 날짜의 null만 막으면 된다고 생각했는데, 프론트가 현재 환율을 미리 채워서 항상 숫자를 보내고 있어 그 검사가 무효였습니다.

> 원인은 서버가 자동으로 보인 값인지 사용자가 직접 입력한 값인지 구분할 수 없는 API 계약이었습니다. 그래서 `exchangeRateMode`를 AUTO와 MANUAL로 나눴습니다. 과거 외화 거래는 MANUAL만 허용하고, AUTO 요청이 환율 숫자를 보내면 오히려 거부합니다. 화면 문제가 아니라 계약 문제로 해결한 사례입니다.

### 1-6. 실패 처리 원칙 — 1분 10초

> 프로젝트 전체에는 Unknown Preservation, 즉 불확실성 보존이라는 원칙을 적용했습니다. 시스템이 모르는 외부 사실을 0이나 1, 현재값으로 채워서 그럴듯한 숫자를 만들지 않는다는 원칙입니다.

> 시세 제공자가 장애일 때 자산 등록은 허용합니다. 현재가는 null로 저장해도 나중에 복구할 수 있고 자산의 정체성은 유지되기 때문입니다. 반면 과거 거래 환율이 없으면 원화 평단가를 확정할 수 없으므로 거래를 중단합니다. 하나는 불완전한 상태를 정직하게 저장할 수 있고, 다른 하나는 도메인 불변식이 깨진다는 차이입니다.

> 조회에서는 만료된 last-good 값을 쓸 수 있지만 stale과 갱신 시각을 함께 보여줍니다. 한 자산의 평가가 불가능할 때는 나머지만 더한 부분합을 총자산처럼 표시하지 않고 총액을 알 수 없음으로 둡니다.

### 1-7. 정합성·보안 — 1분

> 인가는 검사를 잘 쓰는 것보다 빠뜨릴 수 없게 만드는 데 집중했습니다. 요청에서 userId를 받지 않고 JWT의 SecurityContext에서만 가져옵니다. Asset 단건 조회 Repository도 id만 받는 메서드 대신 id와 userId를 항상 함께 받습니다. 타인 자산과 없는 자산은 모두 404로 응답해 리소스 존재 여부도 노출하지 않습니다.

> 동시 수정은 Asset의 Version을 사용한 낙관적 락으로 막습니다. 같은 Asset에 8건을 동시에 보냈을 때 1건만 반영되고 7건은 409로 실패해 Lost Update가 없음을 확인했습니다. 정산 자산이 공용 경합 지점이 될 수 있다는 한계는 알고 있지만, 사용자별·통화별 저동시성의 수동 입력 MVP라는 가정에서 유지했습니다.

> 자동 재시도는 넣지 않았습니다. 멱등성 키 없이 재시도하면 사용자의 중복 클릭을 정상 거래 두 건으로 만들 수 있기 때문입니다.

### 1-8. 구현 중 배운 점 — 55초

> 가장 크게 배운 점은 외부 API의 실패를 성공과 실패 두 가지로만 나누면 안 된다는 것입니다. Yahoo가 429를 반환했을 때 처음에는 잘못된 심볼로 처리해 정상 종목 등록까지 막았습니다. 지금은 404처럼 심볼이 확실히 없는 경우와 429·5xx·타임아웃 같은 제공자 장애를 분리합니다.

> 또 PRD의 append-only 원칙도 그대로 유지하지 않았습니다. 사람이 수동으로 입력하는 서비스에서는 오타 정정이 필수이기 때문입니다. 거래를 삭제할 때는 중간 거래 이후의 평단과 실현손익이 모두 바뀔 수 있어 남은 이력을 시간순으로 replay합니다. 원칙을 깬 것이 아니라, 원칙이 적용되는 조건을 다시 정의한 경험이었습니다.

### 1-9. 마무리와 피드백 요청 — 45초

> 현재 구현은 개인용 MVP로는 동작하지만 운영 수준이라고 주장하지는 않습니다. Yahoo의 비공식 API, 조회 시 Snapshot과 시세를 갱신하는 구조, 커진 Asset Aggregate, 멱등성 없는 409 처리 같은 한계가 있습니다.

> 다음 단계에서는 외부 FX 조회를 거래 트랜잭션 밖에서 끝내고 확정값만 전달하는 경계를 만들고, Asset의 Position과 MarketData 책임을 분리하는 리팩터링을 우선하고 싶습니다.

> 오늘은 기능이 많아 보이는지보다 세 가지에 대한 피드백을 받고 싶습니다. Asset과 Transaction의 경계가 적절한지, Unknown Preservation 원칙이 사용자 편의와 정합성 사이에서 균형적인지, 그리고 현재 규모에서 가장 먼저 분리해야 할 책임이 무엇인지 의견을 듣고 싶습니다.

## 2. 3분 압축 대본

발표 시간이 갑자기 줄었을 때 이 버전만 말한다.

> Folio는 현금·은행·주식·암호화폐를 직접 기록하고 최신 시세와 환율로 원화 Portfolio를 보여주는 개인 자산 대시보드입니다. 주문이나 MyData 연동보다 수동 입력에서 숫자가 틀리지 않는 문제에 집중했습니다.

> 핵심 설계는 세 가지입니다. 첫째, Asset을 Aggregate Root로 두고 수량·평단·실현손익을 도메인 메서드에서만 바꿉니다. 매수와 매도는 같은 통화의 대기자금까지 하나의 트랜잭션으로 정산합니다.

> 둘째, 현재 가치와 취득 원가를 분리했습니다. 현재 평가금액은 현재가와 현재 환율로 계산하지만, 원화 평균 매입단가는 거래 당시 환율로 확정합니다. 프론트가 자동으로 넣은 환율과 사용자 입력을 서버가 구분하지 못해 과거 원가가 오염된 버그가 있었고, `exchangeRateMode=AUTO/MANUAL`이라는 API 계약으로 해결했습니다.

> 셋째, Unknown Preservation 원칙을 사용합니다. 시세를 모르면 null이나 stale로 표시하지 0이나 현재값으로 꾸미지 않습니다. 등록은 불완전한 상태로 저장해 나중에 복구할 수 있지만, 과거 거래 환율처럼 원가 불변식을 깨는 값은 저장을 중단합니다.

> 사용자 오입력도 중요한 도메인으로 봤습니다. 최초 수량은 가짜 매도 없이 정정하고, 잘못된 거래는 삭제 후 전체 이력을 시간순 replay합니다. 인증 사용자는 요청에서 받지 않고 SecurityContext에서만 가져오며, 소유권은 Repository 조회 조건에 강제했습니다.

> 현재 한계는 비공식 시세 API, 커진 Asset Aggregate, 낙관적 락 충돌의 409 처리입니다. Asset과 Transaction의 경계, 불확실성 처리 원칙, 다음 리팩터링 우선순위에 대한 피드백을 받고 싶습니다.

### 데모에서 피할 것

- 발표 당일 처음으로 Docker 이미지를 빌드하지 않는다.
- 외부 시세 숫자가 특정 값일 것이라고 말하지 않는다. 시장과 제공자 상태에 따라 바뀐다.
- `DEMO HISTORY`를 실제 90일 운영 데이터라고 말하지 않는다.
- H2로 실행했다면 “재시작해도 데이터가 남는다”고 말하지 않는다.
- 이메일 중복확인을 이메일 본인 인증이라고 부르지 않는다.
- 금액 가리기를 암호화나 보안 기능이라고 부르지 않는다.
- “동시성 문제를 완전히 해결했다”고 말하지 않는다. Lost Update를 감지하고 409로 거부한다고 말한다.

상세 실행 순서는 [DEMO.md](DEMO.md)를 따른다.

## 4. 설계 개념 공부 노트

발표 전에 아래의 “내 말로 설명하기”를 소리 내어 답해본다. 막히는 항목이 있으면 그 항목을 질문하면 된다.

### 4-1. Aggregate Root

정의:

> 관련 객체 묶음의 정합성을 지키는 유일한 진입점이다. 외부에서는 Aggregate 내부 상태를 마음대로 바꾸지 않고 Root의 도메인 메서드를 통한다.

이 프로젝트에서:

- Root: `Asset`
- 지키는 불변식: 수량 음수 금지, 유형과 거래 종류 일치, 평단·실현손익 계산 일관성
- Service 역할: 요청 순서와 Repository를 조율
- Asset 역할: 계산과 상태 변경

내 말로 설명하기:

> “TransactionService에서 수량을 직접 더하지 않고 Asset에 맡긴 이유는 무엇인가?”

핵심 답: 계산 규칙의 변경 지점을 한곳으로 모으고 어느 API 경로에서도 같은 불변식을 적용하기 위해서다.

### 4-2. DB Transaction과 금융 Transaction의 차이

- DB Transaction: 여러 DB 변경을 모두 성공시키거나 모두 롤백하는 원자성 경계
- 금융 Transaction Entity: 매수·매도·입금·출금이라는 사용자의 사건 기록

이 프로젝트의 매수 한 건은 `투자 Asset 변경 + 정산 Asset 변경 + Transaction 저장`을 하나의 DB Transaction으로 묶는다.

내 말로 설명하기:

> “매수 Transaction row는 저장됐는데 USDT 잔액 차감이 실패하면 어떻게 되는가?”

핵심 답: 같은 DB 트랜잭션이므로 전체 롤백되어 둘 다 남지 않는다.

### 4-3. 낙관적 락

정의:

> 충돌이 드물다고 보고 먼저 작업하되, 커밋할 때 version이 바뀌었는지 확인해 충돌을 감지하는 방식이다.

비관적 락과 비교:

| 방식 | 동작 | 이 프로젝트 판단 |
|---|---|---|
| 비관적 락 | 먼저 행을 잠그고 다른 요청을 기다리게 함 | 수동 입력·저동시성에 매번 대기 비용을 주지 않음 |
| 낙관적 락 | 평소 잠그지 않고 충돌 시 한 요청을 실패시킴 | `@Version`, 409 응답으로 채택 |

주의: 낙관적 락이 요청을 순서대로 모두 성공시키는 것은 아니다. Lost Update를 조용히 허용하지 않고 충돌을 드러낸다.

### 4-4. 멱등성

정의:

> 같은 요청을 여러 번 보내도 결과가 한 번 보낸 것과 같게 만드는 성질이다.

왜 자동 재시도 전에 필요한가:

> 네트워크 오류 후 서버가 실제로 매수를 저장했는지 클라이언트가 모르는 상태에서 다시 보내면 거래가 두 번 생길 수 있다. 요청별 idempotency key가 있으면 서버가 이미 처리한 요청인지 구분할 수 있다.

현재 답:

> “현재는 충돌 시 409로 실패시킵니다. 자동 재시도를 넣으려면 멱등성 키가 먼저 필요하고 별개 작업이라 MVP에서 제외했습니다.”

### 4-5. Replay

정의:

> 사건을 정해진 순서로 처음부터 다시 적용해 현재 상태를 재구성하는 방식이다.

왜 필요한가:

> 중간 매수가 삭제되면 이후 매도 시점의 평단가가 달라진다. 삭제된 거래의 수량만 빼서는 실현손익을 복구할 수 없다.

Event Sourcing과의 차이:

> 이 프로젝트는 완전한 Event Sourcing이 아니다. Asset 테이블에 현재 상태를 함께 저장하고 Transaction은 정정 시 재계산의 근거로 활용한다. 현재 상태를 매 조회마다 이벤트에서 전부 재구성하지 않는다.

### 4-6. Snapshot

정의:

> 특정 시점의 계산 결과를 저장해 이후 비교 기준으로 사용하는 값이다.

Daily PnL:

```text
오늘 손익 = 현재 Portfolio 가치 - 기준 Snapshot 가치 - 기준 이후 순외부유입
순외부유입 = 입금 - 출금
```

매수·매도는 Portfolio 내부 이동이라 외부유입에 포함하지 않는다.

현재 한계: 조회 시 하루 한 점을 만들기 때문에 앱을 쓰지 않은 과거 날짜의 실제 역사값은 생성하지 못한다. 데모 데이터는 명시적으로 `DEMO HISTORY`다.

### 4-7. Stale과 Last-good

- fresh: TTL 안에 있는 최신값
- stale: TTL은 지났지만 마지막으로 성공했던 값
- missing: 성공한 값이 한 번도 없음

stale을 허용하는 이유: 조회는 다음 성공 때 복구되고, 갱신 시각을 함께 보여주면 사용자가 불확실성을 판단할 수 있다.

stale을 과거 거래 원가에 쓰지 않는 이유: 한번 원가로 저장되면 영구 계산값이 되어 다음 조회로 자동 복구되지 않는다.

### 4-8. DTO와 Entity

- Entity: DB 영속성과 도메인 상태를 가진 내부 모델
- Request DTO: 외부 입력 계약과 validation
- Response DTO: 화면에 필요한 표현 계약

Entity를 그대로 응답하지 않은 이유:

> 내부 필드와 API 계약이 결합되고, 지연 로딩·민감정보 노출·순환 참조 가능성이 생기며, 화면 변경이 DB 모델 변경으로 번질 수 있기 때문이다.

### 4-9. 외부 I/O와 트랜잭션 경계

문제:

> DB 트랜잭션과 커넥션을 잡은 채 Yahoo 응답을 2초 기다리면 요청이 몰릴 때 커넥션 풀이 고갈될 수 있다.

현재 시세 갱신:

```text
짧은 DB 조회 종료 → 외부 HTTP → 성공값만 별도 짧은 DB 반영
```

주의: 현재 거래 경로는 `FxRateQueryService`를 호출하지 않는다. 앞으로 전역 FX를 거래 AUTO에 연결할 때도 HTTP를 트랜잭션 밖에서 먼저 끝내야 한다.

### 4-10. TOCTOU

정의:

> 확인한 시점(Time of Check)과 실제 사용 시점(Time of Use) 사이에 상태가 바뀌는 경쟁 조건이다.

예:

> 바깥에서 USDT 잔액이 충분한지 확인한 뒤 환율 API를 호출하는 동안 다른 요청이 잔액을 쓸 수 있다.

해결 원칙:

- 바깥 검증은 불필요한 외부 호출을 줄이는 빠른 실패용
- 트랜잭션 안쪽 검증이 진짜 정합성 관문
- 최종 변경은 낙관적 락으로 충돌 감지

## 5. 예상 질문과 답변

### Q1. “Asset 엔티티가 772줄인데 너무 큰 것 아닌가요?”

> 맞습니다. 처음보다 opening position, 현재 시장 데이터, 정산, 정정 책임이 늘면서 772줄과 21개 영속 필드까지 커졌습니다. 현재는 불변식을 한곳에서 지키는 장점을 우선했지만 분리 시점에 도달했다고 봅니다. 다음 단계에서는 수량·원가·실현손익을 `PositionState`, 현재가·환율·갱신시각을 `MarketData`로 묶되 Aggregate Root는 Asset으로 유지하는 방향을 검토하고 있습니다.

좋은 태도: 방어하지 말고 현재 비용을 인정한 뒤 분리 기준을 말한다.

### Q2. “Transaction을 별도 Repository로 두면 Aggregate 경계를 깨는 것 아닌가요?”

> 엄격한 의미에서는 Transaction도 Asset Aggregate 안에 있다고 볼 수 있습니다. 하지만 계속 늘어나는 거래 컬렉션을 Asset 조회 때마다 로딩하는 비용을 피하려고 영속 조회는 분리했습니다. 대신 Transaction을 단독으로 변경하지 않고 부모 Asset의 소유권과 도메인 규칙을 먼저 통과하게 했습니다. 개념적 소유권과 저장 최적화를 구분한 실용적 절충입니다.

### Q3. “왜 처음 보유 수량을 BUY 거래로 만들지 않았나요?”

> 사용자는 서비스를 쓰기 전부터 자산을 보유할 수 있습니다. 정확한 체결 이력이 없는데 가짜 BUY를 만들면 사건 로그가 거짓이 됩니다. 그래서 opening position은 기준 상태로 두고, 이후 실제 입력부터 Transaction으로 기록했습니다.

### Q4. “수량 정정도 이벤트로 남겨야 하지 않나요?”

> 감사 추적이 중요한 운영 금융 서비스라면 correction event가 더 적합합니다. 현재 MVP는 개인 수동 입력의 편의와 현재 상태 복구에 집중해 opening baseline을 수정하고 기존 거래를 replay합니다. 누가 언제 무엇을 고쳤는지 감사 로그가 필요해지는 시점에는 별도 correction event로 확장해야 합니다.

### Q5. “거래 삭제가 append-only와 모순되지 않나요?”

> 맞습니다. 그래서 원칙의 적용 범위를 바꿨습니다. 시스템이 확정한 체결 이벤트라면 append-only가 맞지만, 사람이 손으로 옮겨 적은 데이터에는 오타 정정 경로가 필요합니다. 현재는 삭제 후 replay를 선택했고, 운영 감사 요구가 생기면 원본 보존과 correction event 방식으로 바꿔야 합니다.

### Q6. “왜 시세가 없을 때 자산 등록은 허용하면서 거래는 막나요?”

> 차이는 불완전한 상태를 정직하게 저장할 수 있는가입니다. 현재가는 null로 저장해도 Asset의 정체성과 수량은 유효하고 나중에 복구됩니다. 거래 환율이 null이면 원화 평단과 실현손익이라는 불변식을 확정할 수 없습니다. 그래서 등록은 허용하고 거래는 중단합니다.

### Q7. “과거 거래 환율을 왜 서버가 자동으로 찾아주지 않나요?”

> 현재 Provider는 현재 환율을 위한 것이고 과거 체결 시각의 공식 환율 데이터 계약이 없습니다. 오늘 환율을 자동 대입하는 것이 가장 위험하므로 MANUAL을 요구했습니다. 과거 환율 Provider를 도입하면 출처와 기준시각을 함께 저장하는 방식으로 자동화할 수 있습니다.

### Q8. “현재 손익에 환율 영향과 종목 가격 영향이 섞이지 않나요?”

> 섞입니다. 현재 목표는 사용자가 실제 원화로 얼마를 보유하는지 보는 것이므로 총 원화 손익을 우선했습니다. 가격 손익과 FX 손익을 분리하려면 기준 환율과 계산 정의가 하나 더 필요해 MVP에서 제외했고 Roadmap으로 명시했습니다.

### Q9. “왜 USDT를 팔면 KRW가 아니라 USDT가 늘어나나요?”

> 거래의 원래 결제 통화를 보존하기 위해서입니다. USDT 마켓에서 매도한 결과는 USDT 잔액입니다. 원화로 바꾸는 것은 별도의 환전 또는 출금 사건이어야 하고, 현재 Portfolio 총액을 보여줄 때만 USDT/KRW를 적용합니다.

### Q10. “매수 한 번에 Asset 두 개를 바꾸는데 데드락은 없나요?”

> 현재는 명시적 비관적 행 잠금을 사용하지 않고 낙관적 락으로 커밋 충돌을 감지합니다. 따라서 전통적인 `SELECT FOR UPDATE` 잠금 순서 데드락 가능성은 낮지만, 같은 정산 자산의 version 충돌은 발생할 수 있습니다. 사용자별·통화별 저동시성 MVP라는 가정에서 409로 드러내고 있습니다. 규모가 커지면 두 Asset 조회 순서를 ID 기준으로 고정하거나 Wallet/Ledger 모델을 별도로 검토해야 합니다.

### Q11. “BTC와 ETH를 동시에 사도 USDT 대기자금에서 충돌하지 않나요?”

> 맞습니다. 정산 연동 이후 경합 지점이 개별 종목에서 공용 USDT 자산으로 넓어졌습니다. 그래서 낙관적 락의 근거를 ‘동일 Asset 충돌이 드물다’가 아니라 ‘사용자별·동일 통화의 수동 입력 동시성이 낮다’로 정정했습니다. 이 가정이 깨지는 자동 연동 서비스라면 현재 모델을 재검토해야 합니다.

### Q12. “409가 나면 자동 재시도하면 되지 않나요?”

> 단순 재시도는 동일 매수를 두 번 만들 수 있습니다. 멱등성 키로 같은 사용자 의도를 식별한 뒤에만 안전한 재시도를 넣을 수 있어 현재는 409와 재입력 안내까지만 구현했습니다.

### Q13. “GET Dashboard가 DB를 갱신하는 것은 REST 원칙 위반 아닌가요?”

> 엄밀히 safe하지 않은 절충입니다. 갱신 대상은 사용자가 입력한 원본이 아니라 외부 시세의 파생 캐시이고 같은 요청을 반복해도 비즈니스 사건이 추가되지는 않습니다. MVP에서는 최신 조회 경험을 우선했지만 자산과 사용자가 늘면 Scheduler가 미리 갱신하고 GET은 읽기만 하도록 바꾸는 것이 맞습니다.

### Q14. “외부 API를 DB 트랜잭션 안에서 호출하나요?”

> 현재 시세 갱신은 DB 조회를 끝낸 뒤 HTTP를 호출하고 성공값만 별도 트랜잭션으로 반영합니다. 현재 거래 경로는 전역 FX 서비스를 호출하지 않습니다. 향후 AUTO 환율을 통합할 때도 외부 조회를 먼저 끝내고 확정값만 짧은 거래 트랜잭션에 전달하는 경계를 만들 계획입니다.

### Q15. “시세 캐시의 synchronized 안에서 HTTP를 호출하면 스레드가 기다리지 않나요?”

> 같은 심볼 요청은 기다립니다. 의도적으로 한 요청만 외부로 보내 thundering herd를 막는 선택입니다. 다만 심볼별 락이라 NVDA 요청이 BTC 요청을 막지는 않습니다. 현재 미스 심볼 조회는 순차이므로 자산 수가 크게 늘면 비동기 병렬화와 Provider rate limit을 함께 설계해야 합니다.

### Q16. “왜 stale 값을 보여줘도 괜찮다고 판단했나요?”

> 조회값은 갱신 시각과 stale 상태를 함께 보여주고 다음 성공 시 자동 복구할 수 있습니다. 반면 거래 원가처럼 영구 계산에 들어가는 값에는 stale을 자동 적용하지 않습니다. 쓰기는 엄격하고 읽기는 불확실성을 노출한 채 관대하게 처리한 이유입니다.

### Q17. “한 종목 시세가 없다고 총자산 전체를 숨기는 것은 과하지 않나요?”

> 부분합을 ‘총자산’이라고 표시하면 완전한 값처럼 오해할 수 있습니다. 각 행의 확인 가능한 값은 계속 보여주되 총액은 `-`와 경고로 표시했습니다. 향후에는 ‘확인된 자산 합계’와 ‘평가 불가 N건’을 별도 표현하는 UX도 가능합니다.

### Q18. “Analysis가 Roadmap 기능이었는데 Batch 없이 어떻게 만들었나요?”

> 대규모 과거 시세 재구축 대신 사용자가 조회한 날의 Portfolio 총액을 하루 한 점 Snapshot으로 저장했습니다. 09시 KST를 날짜 경계로 사용하고 입출금을 보정해 오늘 손익을 계산합니다. 따라서 사용 시작 전 과거를 복원하지는 못하며, 발표용 이력은 `DEMO HISTORY`라고 명시했습니다.

### Q19. “왜 타인 자산 접근을 403이 아니라 404로 응답하나요?”

> 403은 해당 ID의 자산이 존재한다는 사실을 알려줍니다. 자산 ID를 순회해 리소스 존재를 추측하지 못하도록 타인 자산과 없는 자산을 같은 404로 처리하고, 서버 내부 로그에서만 접근 거부를 구분합니다.

### Q20. “이메일 중복확인 API는 계정 존재를 노출하지 않나요?”

> 가입 UX를 위해 사용 가능 여부를 명시적으로 보여주는 절충이라 계정 존재 추측 가능성은 있습니다. 운영 서비스라면 rate limit, CAPTCHA, 모니터링을 추가하거나 정책에 따라 응답을 더 일반화해야 합니다. 로그인 실패 메시지는 이메일과 비밀번호 중 어느 쪽이 틀렸는지 구분하지 않습니다.

### Q21. “로그아웃 API가 왜 없나요?”

> 현재 JWT는 서버 세션을 저장하지 않는 stateless 구조라 프론트가 토큰을 삭제해 로그아웃합니다. 단점은 유출된 토큰이 24시간 만료 전까지 유효하다는 점입니다. 즉시 폐기가 필요하면 짧은 access token과 refresh token, revoke list 같은 서버 상태가 필요합니다.

### Q22. “비밀번호 확인을 서버가 받지 않는 이유는?”

> 비밀번호 확인은 사용자가 같은 문자열을 두 번 입력했는지 보는 UI 검증이고 저장할 도메인 데이터가 아닙니다. 서버는 실제 password 하나의 길이와 유효성만 검증하고 BCrypt로 저장합니다.

### Q23. “Yahoo Finance를 왜 썼나요?”

> 비용 없이 국내외 주식 MVP를 빠르게 검증하기 위해 사용했습니다. 대신 Provider 인터페이스 뒤에 숨기고, 비공식 API의 429와 응답 변경 위험을 문서화했습니다. 실제 서비스 전환 우선순위는 공식 또는 계약 기반 API로 교체하는 것입니다.

### Q24. “왜 MyData나 거래소 지갑 연동을 안 했나요?”

> 이번 문제는 데이터 수집 채널보다 Portfolio 모델과 사용자 입력 경험을 검증하는 것이었습니다. 연동을 넣으면 인증·동의·기관별 계약·동기화 충돌이 프로젝트의 중심이 됩니다. 의도적으로 범위를 줄여 도메인 정합성과 실패 처리에 시간을 썼습니다.

### Q25. “H2에서 되는데 MySQL에서도 된다고 볼 수 있나요?”

> Docker MySQL 프로필을 제공하고 기본 흐름은 같은 JPA 모델을 사용하지만, H2 호환 모드가 MySQL을 완전히 대체하지는 않습니다. 현재 migration 도구와 CI의 DB 통합 테스트가 없으므로 운영 호환성을 보장한다고 말하지 않습니다. 발표 데모의 재현성은 H2, 지속 데이터 검증은 MySQL 프로필의 역할입니다.

### Q26. “테스트 49개라고 했는데 단위 테스트인가요?”

> 구분해야 합니다. JUnit은 11개 클래스의 35개 테스트이고, `verify.sh`는 실행 중인 서버에 실제 HTTP 요청을 보내는 49개 assertion입니다. 둘을 합친 숫자로 말하지 않고 각각의 역할을 설명합니다.

모르는 것을 아는 척하는 것보다 현재 사실, 판단, 확인 방법을 분리하면 답이 훨씬 강해진다.

### 권장 문장 구조

> “그 부분은 현재 코드에서 검증하지 못했습니다. 지금 확실히 말씀드릴 수 있는 것은 A까지이고, B는 C 조건에서 문제가 될 수 있다고 생각합니다. 확인한다면 D 테스트를 먼저 만들고 판단하겠습니다.”

예시:

> “여러 인스턴스에서 캐시 동시성이 유지되는지는 현재 검증하지 못했습니다. 지금 캐시는 단일 JVM의 ConcurrentHashMap이라 인스턴스 간에는 공유되지 않습니다. 다중 인스턴스가 필요하면 Redis 같은 공용 캐시로 Provider 경계를 교체하고 동시 호출 수를 측정하겠습니다.”

### 피해야 할 답

- “개인 프로젝트라 상관없습니다.”
- “Spring이 알아서 해줍니다.”
- “나중에 하면 됩니다.”
- “아마 문제없을 겁니다.”

### 바꿔 말하기

- “MVP의 저동시성 가정에서는 위험을 수용했고, 가정이 깨지는 조건은 이것입니다.”
- “현재 Spring의 이 기능에 기대고 있고, 코드상 강제 지점은 여기입니다.”
- “후속 과제로 미룬 이유는 우선순위와 회귀 위험이며, 먼저 필요한 전제는 이것입니다.”
- “아직 확인하지 않았고, 이 테스트로 검증할 수 있습니다.”
