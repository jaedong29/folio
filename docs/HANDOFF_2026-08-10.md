- `1 BTC / 평균 매수가 60,000 USDT / 당시 환율 1,400`처럼 현재 Position을 등록하면 원통화 평단과 KRW 원가 평단이 함께 저장된다.

## 3. 최초 재정리 MD 이후 구현한 내용

### 3-1. 최초 Position 등록

과거 거래를 전부 복원하지 않고 현재 보유량부터 등록할 수 있다.

- `AssetCreateRequest.quantity`: 현재 보유 수량, 생략 시 0
- `averagePrice`: 원래 통화 기준 평단, 선택값
- `averageExchangeRate`: 평균 매입 당시 원/통화 환율, 선택값
- 최초 보유량은 가짜 BUY Transaction을 만들지 않고 Asset의 opening position으로 저장한다.
- 평단을 모르면 평가금액은 보여주되 평가손익과 수익률은 `-`로 표시한다.

중요한 환율 계산:

```text
매입 원가(KRW) = 최초 수량 × 매입 단가(원통화) × 매입 당시 환율
현재 평가액(KRW) = 현재 수량 × 현재 가격(원통화) × 현재 환율
평가손익 = 현재 평가액 - 현재 보유분의 원가
```

즉 미국주식을 1,060 USD, 환율 1,520원일 때 매수했다면 원가는 당시 환율로 고정하고, 현재 910 USD의 평가액은 **현재 환율**로 계산한다. 과거 환율로 현재 평가액까지 계산하거나 현재 환율로 과거 원가를 덮어쓰지 않는다.

### 3-2. 사용자 입력 심볼과 조회 심볼 UX

- Crypto 사용자는 `BTCUSDT` 대신 `BTC`를 입력한다.
- STOCK은 시장을 `KOSPI / KOSDAQ / OVERSEAS`로 선택한다.
- `000660 + KOSPI`는 내부 조회용으로 `000660.KS`로 정규화한다.
- 화면에는 `displaySymbol`을 사용해 provider 접미사를 숨긴다.
- 현재 구조는 별도 Symbol Master 테이블까지 만들지 않고 DTO 정규화와 표시 심볼 분리로 해결했다.
- 국내주식은 KRX KIND KOSPI/KOSDAQ 2,595개 정적 카탈로그를 브라우저에서 검색한다.
- `SK`, `하이닉스`, `000660` 검색 결과에서 SK하이닉스를 선택하면 이름·코드·시장·KRW가 자동 입력된다.
- 검색은 외부 API를 매 타이핑마다 호출하지 않으며, `scripts/update-krx-securities.py`로 스냅샷을 갱신한다.
- 해외주식·암호화폐 자동완성은 아직 미구현이다.

### 3-3. 현재가와 환율

- Crypto 현재가: Binance Spot
- STOCK 현재가: Yahoo Finance
- USD/KRW: Yahoo Finance
- USDT/KRW: Upbit public ticker
- 시세·환율은 15분 캐시, 마지막 성공값 폴백, 갱신 시각을 사용한다.
- 사용자가 우상단 새로고침을 누르면 `force=true`로 TTL을 무시하고 최신 조회를 시도한다.
- 같은 심볼의 동시 캐시 미스는 symbol 단위 동기화로 중복 호출을 줄인다.
- 현재가를 확보하지 못한 자산은 0원으로 만들지 않고 `valuationKRW=null`로 둔다.
- 한 자산이라도 평가 불가하면 총액도 잘못된 부분합 대신 `null`로 응답한다.

프론트 새로고침은 Dashboard를 먼저 요청해 시세 반영을 끝낸 뒤 Portfolio와 Asset 목록을 조회한다. 동일 Asset을 Dashboard와 Portfolio가 동시에 갱신해 낙관적 락 충돌을 만드는 문제를 줄이기 위한 순서다.

### 3-4. KRW/USD/USDT 기본 투자 대기자금

사용자가 첫 매도 전에 정산 자산을 따로 추가해야 하는 마찰을 없앴다.

- 신규·기존 사용자에게 KRW, USD, USDT CASH Asset을 각각 0으로 준비한다.
- 잔액이 0이어도 Dashboard의 투자 대기자금에 표시한다.
- 기본 대기자금은 삭제할 수 없고 잔액을 조정하도록 안내한다.
- 추가 BANK/CASH 자산은 사용자가 별도로 등록할 수 있다.

### 3-5. BUY/SELL 정산 연결

BUY/SELL은 Portfolio 내부 자산 이동으로 구현했다.

```text
ZEC 매수: USDT 대기자금 감소 + ZEC 증가
ZEC 매도: ZEC 감소 + USDT 대기자금 증가
MU 매수:  USD 대기자금 감소 + MU 증가
MU 매도:  MU 감소 + USD 대기자금 증가
```

- 매매 요청은 같은 통화의 `settlementAssetId`를 필수로 받는다.
- 거래 자산과 정산 자산은 같은 DB 트랜잭션에서 원자적으로 변경된다.
- 정산 금액은 원화로 바꾸지 않고 원래 통화 수량으로 CASH/BANK에 반영한다.
- `Transaction.settlementAssetId`, `settlementAmount`로 연결을 남긴다.
- BUY/SELL 정산을 별도 DEPOSIT/WITHDRAW 이벤트로 만들지 않는다. 그래야 Daily PnL의 외부 자금 흐름과 섞이지 않는다.
- 거래 삭제 시 대응 정산 이동도 함께 되돌린다.

분리된 에러:

- `INSUFFICIENT_ASSET_QUANTITY`: 매도할 투자 자산 수량 부족
- `INSUFFICIENT_SETTLEMENT_FUNDS`: 매수대금을 낼 대기자금 부족 또는 매도 삭제 시 되돌릴 대기자금 부족
- `SETTLEMENT_CURRENCY_MISMATCH`: 매매 자산과 대기자금 통화 불일치
- `CONCURRENT_MODIFICATION`: 낙관적 락 충돌

에러 메시지에는 문제가 된 자산명·심볼·통화와 보유/요청 수량을 포함한다. 매도 거래 삭제 시 이미 매도대금을 출금한 경우에도 `INSUFFICIENT_SETTLEMENT_FUNDS`로 정확히 분류하도록 수정했다.

### 3-6. 거래 환율 계약 — `exchangeRateMode`

가장 중요한 데이터 정합성 수정이다.

과거에는 프론트가 자산의 현재 환율을 입력창에 자동 채워 서버에 보내므로, 서버가 그것을 사용자가 확인한 과거 환율인지 자동값인지 구분할 수 없었다. 백엔드에서 단순 null 검사만 추가해도 UI가 항상 숫자를 보내기 때문에 우회되는 구조였다.

이를 다음 계약으로 바꿨다.

| 거래 조건 | 결과 |
|---|---|
| KRW 자산 | 서버가 환율 1 사용 |
| 오늘 + `AUTO` + Asset 현재 환율 있음 | 서버가 저장된 현재 환율 사용 |
| 오늘 + `AUTO` + Asset 현재 환율 없음 | 400, 수동 입력 안내 |
| 오늘 + `MANUAL` + 환율 있음 | 사용자 입력값 사용 |
| 과거 날짜 + `MANUAL` + 환율 있음 | 사용자 입력값 사용 |
| 과거 날짜 + `AUTO` | 400, 당시 환율 입력 요구 |
| `AUTO`인데 `exchangeRate` 숫자도 전송 | 400, 계약 위반을 즉시 노출 |

프론트 동작:

- 오늘 거래 화면에는 현재 환율을 참고용으로 보여줄 수 있다.
- 사용자가 수정하지 않았다면 요청에는 숫자를 보내지 않고 `exchangeRateMode=AUTO`만 보낸다.
- 사용자가 환율 필드를 직접 수정하면 `MANUAL`로 전환한다.
- 과거 날짜를 선택하면 자동 입력값을 즉시 비운다.
- 날짜를 먼저 고른 뒤 자산을 바꿔도 과거 거래에 현재 환율이 다시 주입되지 않게 했다.
- 매매 폼과 입출금 폼에 같은 규칙을 적용했다.
- `seed-demo.sh`와 `verify.sh`의 과거 거래는 모두 `MANUAL`을 명시한다.

현재 환율은 Asset의 현재 평가용 상태이고, Transaction의 환율은 거래 당시 원가·실현손익 재계산용 스냅샷이다. 거래 입력이 `Asset.updateExchangeRate()`를 호출해 현재 환율을 덮어쓰지는 않는다.

### 3-7. 알 수 없는 JSON 필드 거부

`spring.jackson.deserialization.fail-on-unknown-properties=true`를 적용했다.

예를 들어 사용자가 `quantity` 대신 `initialQuantity`를 보내면 조용히 0으로 저장하지 않고 `400 INVALID_INPUT`을 반환한다. 응답에는 잘못된 필드명과 해당 DTO가 허용하는 필드 목록을 포함한다.

이 기능은 수동 입력 기반 MVP에서 오타가 영구적인 잘못된 숫자가 되는 문제를 막는다.

### 3-8. 거래 오입력 정정 — 삭제 후 replay

잘못 입력한 BUY/SELL은 반대 매매로 고치지 않는다.

- 반대 매매는 실제로 하지 않은 거래를 추가하고 실현손익과 대기자금을 오염시킨다.
- 자산 삭제는 Soft Delete 후 복구 정책 때문에 거래 하나를 고치는 방법이 아니다.

구현:

```text
DELETE /api/assets/{assetId}/transactions/{transactionId}
```

- 거래를 삭제한다.
- 남은 거래를 `tradedAt ASC, id ASC` 순서로 다시 replay한다.
- 평단가와 실현손익을 처음부터 재계산한다.
- 대응 정산 자산의 이동도 되돌린다.
- 거래 삭제로 이후 매도 시점의 수량이 음수가 되면 `TRANSACTION_DELETE_BREAKS_HISTORY`로 전체 롤백한다.

이 과정에서 기존 버그도 발견해 수정했다. 과거 날짜 거래를 나중에 입력하면 입력 순서가 아니라 실제 `tradedAt` 순으로 전체 재생해야 평단과 실현손익이 정확하다. 일반적인 최신 거래는 증분 계산을 유지하고, 중간에 끼는 과거 거래만 replay한다.

### 3-9. 최초 보유 수량 오입력 정정

가장 최근 사용자 요구로 추가한 기능이다.

상황:

```text
실제 ZEC 14.7개를 최초 등록하면서 실수로 15.7개 입력
```

1개를 매도 처리하면 가짜 매도와 가짜 실현손익, 가짜 USDT 증가가 생기므로 정정 방법이 아니다. 전체 자산을 삭제하고 다시 등록하는 것도 UX가 나쁘고 Soft Delete 복구 정책과 충돌한다.

구현 API:

```http
PATCH /api/assets/{id}/quantity
Content-Type: application/json

{ "quantity": 14.7 }
```

동작:

- 사용자가 확인한 **현재 실제 보유 수량**을 받는다.
- 신규 거래를 만들지 않는다.
- 실현손익과 정산 대기자금을 인위적으로 움직이지 않는다.
- 현재값과의 차이만큼 opening position을 보정한다.
- 이후 기존 거래를 다시 replay해 평단·실현손익을 일관되게 맞춘다.
- 정정된 opening position으로 과거 SELL이 불가능해지면 전체 롤백하고 거부한다.
- 잘못 입력한 실제 BUY/SELL은 이 기능이 아니라 거래 삭제를 사용하도록 화면에서 설명한다.

화면:

- Asset 상세 드로어에 `수량 정정` 칩을 추가했다.
- 현재 수량과 정정 후 수량, 증감량을 미리 보여준다.
- 정산이나 매매가 발생하지 않는다는 안내를 표시한다.

Daily PnL 처리:

- 오늘 Snapshot 생성 후 수량 정정이 일어나면, 총액 Snapshot만으로 정정분의 기준 시점 가격을 정확히 복원할 수 없다.
- 정정된 1 ZEC를 오늘의 시장 손실처럼 보이지 않게 해당 기준일 Daily PnL을 `unavailable`로 표시한다.
- 다음 09:00 KST Snapshot부터 정정 수량이 기준값에 포함되어 자동 정상화된다.

관련 단위 테스트:

- `correctsOpeningQuantityWithoutCreatingSaleProfit`
- `quantityCorrectionReplaysLaterTradesFromCorrectedOpeningPosition`
- `correctionThatBreaksPastSellIsRejectedWithoutChangingCurrentState`
- `quantityCorrectionAfterBaselineDoesNotAppearAsDailyMarketLoss`

### 3-10. Daily PnL과 Snapshot

Daily PnL은 투자 성과 회계가 아니라 오늘 Portfolio 전체 변화다.

```text
Daily PnL
= 현재 Portfolio 총 KRW 평가액
- 기준 Snapshot 총 KRW 평가액
- 기준 이후 순외부입금액

순외부입금액 = DEPOSIT - WITHDRAW
```

- 기준 경계: 09:00 KST
- Snapshot이 없으면 첫 유효 Portfolio 평가 시점을 baseline으로 생성한다.
- 실제 생성 시각을 저장하고 UI에 표시한다.
- BUY/SELL은 Portfolio 내부 이동이므로 외부 흐름 보정에서 제외한다.
- DEPOSIT/WITHDRAW만 외부 자금 이동으로 센다.
- 기본 대기자금 세 개만 0원으로 존재할 때는 baseline을 만들지 않는다.
- 평가 불가능한 자산이 하나라도 있으면 잘못된 baseline을 만들지 않는다.

Asset Analysis에서는 Snapshot과 현재값을 이용해 1D/7D/30D/90D **순자산 추이**를 보여준다. 입출금 보정이 들어간 투자 수익률 차트라고 부르지 않는다.

발표용 90일 데이터는 `DemoPortfolioHistoryService`가 생성하며 화면에 `DEMO HISTORY`라고 명시한다. 실제 데이터처럼 숨기지 않는다.

### 3-11. 화면 및 UX 개편

디자인 방향은 특정 서비스를 그대로 복제하지 않고 다음 감각을 혼합했다.

- Delta 약 60%: Position 중심, 자산별 시각적 계층
- Kubera 약 25%: 전체 Portfolio와 자산 구성 중심
- Revolut 약 15%: 간결한 동작과 카드 인터랙션

현재 화면:

- Overview: 총 투자자산, 오늘 손익, Position, Allocation, 투자 대기자금, 최근 활동, USD/KRW·USDT/KRW
- Analysis: 오늘 손익을 클릭해 이동, 순자산 차트, 구성, 성과 순위
- Activity: 전체 거래 내역, 유형 필터, 자산/심볼/메모 검색
- Asset Detail: Position 정보, 7일 가격 차트, 거래 이력, 매수/매도, 수량 정정, 이름/시세/환율 수정, 삭제
- `folio.` 브랜드 버튼: Analysis/Activity에서 Overview로 돌아감
- FAB: 자산 등록, 매수·매도, 입금·출금
- 저장 전 거래 결과 미리보기: 거래 후 수량, 정산 잔액, 예상 평단/실현손익, KRW 환산액

- 새로고침 중복 클릭 방지와 진행 상태 표시
- 반응형 레이아웃 및 empty/error/stale 상태

자산 아이콘은 현재 외부 이미지 API에 의존하지 않는다. BTC는 `₿`, ETH는 `Ξ`, 나머지는 유형/심볼 글자 기반 아이콘이다. Upbit/Binance/Yahoo에서 로고를 가져오는 기능은 구현하지 않았다.

## 4. 합의한 설계 원칙과 코드 리뷰 결론

### 4-1. Unknown Preservation — 불확실성 보존 원칙

> 시스템이 모르는 외부 사실은 `null` 또는 `stale`로 보존한다. 필수 계산을 확정할 수 없다면 그럴듯한 숫자를 만들지 않고 입력을 중단한다.

새 필드나 기능을 판단할 때 다음을 확인한다.

1. 모델이 `UNKNOWN`을 null 또는 명시적 상태로 표현할 수 있는가?
2. 그 상태에서도 해당 작업의 도메인 불변식이 유지되는가?
3. 파생 계산이 0, 1, 현재값 같은 대체값을 임의로 만들지 않는가?
4. API와 화면도 불확실성을 그대로 노출하는가?
5. 이후 값을 확보해 복구할 경로가 있는가?

예:

- `currentPrice`: null 저장 후 다음 조회로 복구 가능 → 외부 API 장애 중에도 자산 등록 허용
- BUY/SELL 거래 환율: null이면 원가와 실현손익 확정 불가 → 거래 입력 중단
- 일부 자산 평가 불가: 부분합을 총 투자자산처럼 보이지 않고 총액 null
- 오래된 시세: last-good을 보여주되 `priceStale` 표시

“외부 API가 죽어도 자산 등록은 허용하면서 거래는 왜 막는가?”에 대한 답은 다음과 같다.

> 자산 등록은 `현재가를 모름`이라는 불완전한 상태를 정직하게 저장할 수 있지만, BUY/SELL은 환율 없이 평단과 실현손익을 확정하면 도메인 불변식이 깨지고 잘못된 숫자가 영구 저장되기 때문이다.

### 4-2. 외부 I/O와 트랜잭션 경계

현재 거래 경로는 `FxRateQueryService`를 호출하지 않는다. 따라서 현재 코드에서 거래 트랜잭션 안에 HTTP가 실행되는 문제는 없다.

주의할 함정:

- 후속으로 거래 AUTO 환율에 `FxRateQueryService`를 순진하게 주입하면 `@Transactional buy/sell/deposit/withdraw` 안에서 HTTP가 실행될 수 있다.
- 외부 HTTP를 `synchronized` 안에서 호출하는 서비스까지 TX 안에서 부르면 DB 커넥션을 가진 여러 스레드가 모니터 앞에서 대기할 수 있다.
- 전역 FX 통합 시 반드시 외부 조회를 먼저 끝내고, 확정된 값을 짧은 쓰기 트랜잭션에 전달한다.

후속 구조는 `TransactionFacade`가 아니라 기존 패턴과 용어를 맞춘 `TransactionExecutor` 또는 `TradeExecutor` 계열을 논의했다.

```text
TransactionService (TX 없음)
  1. 빠른 실패용 조회/검증
  2. 외부 환율 확보
  3. TransactionExecutor 실행

TransactionExecutor (@Transactional)
  1. 소유권·통화·잔액 재검증 — 진짜 정합성 관문
  2. Asset + Settlement Asset 변경
  3. Transaction 저장/replay
```

바깥 검증은 외부 API 낭비를 줄이는 빠른 실패용일 뿐이며, TOCTOU 때문에 정합성은 Executor 안쪽 검증이 전적으로 보장해야 한다.

현재 `DashboardFacade`는 읽기 전용 조회 조립기로 사용되므로 쓰기 유스케이스에 Facade라는 이름을 추가하지 않기로 합의했다.

### 4-3. 낙관적 락 유지 근거

정산 연동 이후 BTC와 ETH를 동시에 사도 공용 USDT 대기자금에서 충돌할 수 있다. 따라서 예전의 “같은 Asset 동시 쓰기가 드물다”만으로는 설명이 부족하다.

수정된 근거:

> 대기자금은 서비스 전체 공용이 아니라 사용자별·통화별 한 개이며, 개인용 수동 입력 MVP에서는 동일 사용자가 같은 통화 거래를 동시에 제출할 가능성이 낮다. 이 저동시성 가정 아래 낙관적 락을 유지하고 충돌 시 409로 명시적으로 실패시킨다.

자동 재시도는 아직 넣지 않았다.

> 현재는 충돌 시 409로 실패시킨다. 자동 재시도를 넣으려면 멱등성 키가 먼저 필요하고, 별개 작업이라 MVP에서 제외했다.

### 4-4. 엔티티 표현 로직과 비대화

- `Asset.getMarketLabel()`이 `Binance Spot`, `KOSPI` 같은 표현 문자열을 반환한다.
- `Asset`은 772줄, 21개 영속 필드로 커졌다.
- 현재는 Aggregate Root와 도메인 불변식을 유지한다.
- 다음 단계에서는 수량·원가·실현손익을 `PositionState`, 현재가·환율·갱신 시각을 `MarketData` 값 객체로 묶는 것을 검토한다.
- 발표 직전에 단지 줄 수를 줄이기 위한 분리는 하지 않는다.

## 5. 아직 구현하지 않았거나 의도적으로 남긴 것

### 5-1. 거래 AUTO 환율의 전역 FX 통합

현재 오늘+AUTO 거래는 해당 Asset에 저장된 현재 환율만 사용한다.

```text
오늘 + AUTO + Asset 환율 있음  → 성공
오늘 + AUTO + Asset 환율 없음  → 400, 수동 입력 안내
```

따라서 신규 외화 자산이 아직 환율을 한 번도 확보하지 못했다면 수동 입력이 필요하다. 이는 데이터 오염을 막기 위해 1단계에서 의도적으로 남긴 안전한 실패이며, 완성된 UX는 아니다.

후속 작업:

1. 외부 환율 확보를 거래 DB 트랜잭션 밖으로 이동
2. `TransactionExecutor`로 짧은 원자적 쓰기 경계 분리
3. `FxRateQueryService`의 전역 현재 환율을 AUTO 거래에 사용
4. 실제 HTTP 진입점에서 활성 트랜잭션이 없음을 코드로 단언
5. 실패/동시성 통합 테스트 추가

`Propagation.NEVER` 애노테이션은 자기호출 시 프록시를 통과하지 않는 구멍이 있을 수 있다. 실제 HTTP 메서드에서 `TransactionSynchronizationManager.isActualTransactionActive()`를 검사하는 방안이 더 직접적이라는 의견이 있었다. 아직 구현하지 않았다.

### 5-2. 과거 거래의 날짜 경계

현재 서버와 프론트는 다음처럼 **날짜** 기준으로 과거 여부를 판정한다.

```java
tradedAt.toLocalDate().isBefore(LocalDate.now(KST))
```

자정 00:02에 6분 전인 전날 23:56 거래를 입력해도 과거 거래로 분류되어 수동 환율을 요구한다. 데이터 안전성은 지키지만 UX상 엄격하다.

논의된 대안은 현재 환율 캐시 TTL과 같은 시간 창을 사용하는 것이다.

```text
tradedAt < now(KST) - 15분 → 과거로 취급
```

다만 “오늘 거래”라는 현재 제품 문구와 계약을 바꾸므로 테스트·UI 힌트·서버 타임존을 함께 수정해야 한다. 현재는 미수정 상태다.

### 5-3. DTO 이름

도메인 메서드는 `isValuationBlockedByExchangeRate()`로 의미를 좁혔지만 API DTO와 프론트 필드는 하위 계약 때문에 `exchangeRateMissing`을 유지한다. 실제 요구가 생기면 프론트와 API를 동시에 변경한다.

### 5-4. 추가 기술 부채

- 외부 시세 여러 심볼의 캐시 미스 조회는 순차 처리라 최악의 경우 `2초 × 심볼 수`가 될 수 있다.
- 낙관적 락 자동 재시도와 멱등성 키 없음
- Asset 엔티티의 표현 문자열 책임
- Asset/app.js의 비대화
- MySQL 프로필에 정식 마이그레이션 도구(Flyway/Liquibase) 없음
- 해외주식·암호화폐 검색 자동완성 없음 (국내주식은 정적 KRX 카탈로그로 구현)
- 거래 수수료 모델 없음
- 시장별 개장/마감 상태 표시가 제한적
- TWR/MWR, FIFO, 환차손익 분리, 종목별 Daily attribution 없음

`exchangeRate == 1`을 미입력으로 간주하던 매직값 호환 분기는 제거했다. 실제 환율이 1인 외화도 정상 값으로 인정하는 단위 테스트가 있다.

## 6. 다음 후보 기능 — Portfolio Briefing (아직 미구현)

사용자가 제안했고 방향성만 합의한 기능이다. 일반 뉴스 피드가 아니라 다음 제품 문장으로 정의한다.

> 내 보유자산과 관련된 공식 공시·프로젝트 업데이트·사용 허가가 명확한 뉴스의 최신 이슈를 AI가 한국어 2~3줄로 요약한다.

추천 내비게이션:

```text
Overview | Analysis | Briefing
```

Dashboard에는 최신 1~2건의 작은 미리보기만 두고, 전체는 별도 `Portfolio Briefing` 탭에서 확인한다. 외부 소스 장애가 Overview/Analysis를 깨뜨리면 안 된다.

### 6-1. 가장 작은 MVP 범위

- 보유 중인 자산만 대상
- 자산별 최근 중요 항목 1~3건
- 제목, 출처 유형, 게시 시각, 한국어 AI 요약 2~3줄, 원문 링크
- 필터: 전체 / 공시 / 공식 업데이트
- AI 요약 면책 및 원문 확인 안내
- 30~60분 캐시
- API 키 또는 AI 요약 실패 시 제목·출처·원문 링크는 계속 표시
- 원문 전체를 장기 저장·재배포하지 않고 메타데이터, URL, 제한된 요약, source id/hash 중심 저장
- 각 출처의 이용약관과 라이선스는 별도 확인

### 6-2. 소스 우선순위

1. 국내주식: OpenDART 공시 API
2. 미국주식: SEC EDGAR submissions/API/RSS
3. Crypto: 프로젝트 공식 GitHub Release 또는 공식 RSS
4. 일반 언론 뉴스: 정식 API·RSS·라이선스가 명확한 공급자를 후속 검토

`Apple이 CXMT 메모리를 테스트한다` 같은 언론 단독 보도는 SEC/GitHub만으로 얻을 수 없다. 공식 소스 MVP는 보도 범위가 좁지만 출처와 권리를 설명하기 쉽다. 일반 뉴스는 공급 계약을 확인한 뒤 확장한다.

### 6-3. 중요 설계

LLM에게 심볼 관련성 판정을 전부 맡기지 않는다.

```text
Asset symbol
  → 결정적 SourceMapping (SEC CIK / DART corpCode / GitHub repo / RSS)
  → Source adapter로 수집
  → 정규화·중복 제거·중요도 정렬
  → LLM은 한국어 요약과 보조 분류만 수행
```

예상 데이터 모델:

```text
BriefingSourceMapping
- assetId 또는 normalized symbol
- sourceType
- externalCode (CIK, corpCode, repository 등)

BriefingItem
- assetId
- sourceType
- sourceItemId
- title
- sourceName
- originalUrl
- publishedAt
- summaryKo
- summaryStatus
- sourceTextHash
- fetchedAt
```

### 6-4. 화면 예시

```text
Portfolio Briefing                         최근 업데이트 12분 전
내 보유자산과 관련된 공식 소식을 요약했습니다.

[전체] [공시] [공식 업데이트]

MU                                       SEC · 47분 전
Micron, 신규 실적 보고서 제출
데이터센터 부문 성장과 설비 투자 계획에 관한 내용입니다.
정확한 수치와 맥락은 원문을 확인해주세요.             원문 보기 →

ZEC                              GitHub Release · 2시간 전
Zcash 신규 버전 배포
노드 동기화와 네트워크 안정성 관련 변경이 포함되었습니다.
현재 보유 수량이나 가격 변동을 의미하지는 않습니다.     원문 보기 →
```

안내 문구:

> AI가 생성한 요약으로 원문의 일부 내용이 누락되거나 다르게 해석될 수 있습니다. 투자 판단의 근거가 아니며 정확한 내용은 원문을 확인해주세요.

면책 문구가 콘텐츠 이용 권한을 대신하지는 않는다.

### 6-5. 구현 전 확인할 것

- 실제 보유 자산의 CIK/corpCode/repository 매핑 방식
- 어떤 문서 본문까지 AI 입력으로 사용할 수 있는지 출처별 약관
- AI 키가 없는 데모 폴백
- 중복 공시·수정 공시 처리
- 요약 실패 시 재시도와 상태
- 사용자별 동일 뉴스 중복 저장 여부
- 테스트에서는 외부 API와 LLM을 fixture/fake로 대체할 경계

이 기능은 현재 Portfolio Overview 철학과 잘 맞지만, 핵심 Portfolio 숫자보다 우선하지 않는다. 먼저 설계와 소스 범위를 확정한 뒤 작은 vertical slice로 구현한다.

## 8. 발표에서 설명하기 좋은 핵심 이야기

### 8-1. 환율 버그는 null 검사 문제가 아니라 API 계약 문제였다

```text
처음 처방: 백엔드에서 과거 거래 환율 null 검사
문제: 프론트가 현재 환율을 자동으로 채워 항상 숫자를 보냄
결론: 서버는 자동값과 사용자 확인값을 구분할 수 없었음
해결: exchangeRateMode=AUTO/MANUAL 계약 도입
```

리뷰 지적을 그대로 고친 것이 아니라 처방을 검증하다가 계약 수준의 원인을 찾았다는 사례다.

### 8-2. BUY/SELL과 DEPOSIT/WITHDRAW를 분리했다

- BUY/SELL: Portfolio 내부 자산 형태 변경
- DEPOSIT/WITHDRAW: Portfolio 경계를 넘는 외부 자금 이동
- 이 구분 덕분에 매도해도 총 투자자산이 사라지지 않고 Daily PnL도 입출금에 왜곡되지 않는다.

### 8-3. 사람이 입력하는 이벤트에는 정정 경로가 필요했다

- append-only는 시스템 이벤트에는 강한 원칙이다.
- 수동 입력 MVP에서는 오타를 삭제하거나 수정할 경로가 없으면 사용자가 가짜 반대 거래를 만들게 된다.
- 거래 오타는 삭제+replay, 최초 수량 오타는 opening position 보정+replay로 역할을 나눴다.

### 8-4. 정확히 모르는 숫자는 예쁘게 꾸미지 않았다

- 시세가 없으면 0원이 아니라 `-`
- 전체 평가가 불가능하면 부분합을 총액처럼 보여주지 않음
- 과거 거래 환율을 모르면 현재 환율을 몰래 쓰지 않고 입력 중단
- Snapshot이 부족하면 수익률인 척하지 않고 실제 순자산 추이 또는 계산 불가 상태로 표현
